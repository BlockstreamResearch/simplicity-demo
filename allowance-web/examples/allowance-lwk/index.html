Allowance covenant in-page signing

A benefactor locks testnet L-BTC in a Simplicity covenant; a beneficiary withdraws a fixed amount, no more often than once every N blocks, until it is empty. Everything can run in this page (contract compilation, signing and broadcasting) with no backend and no browser extension, or the same contract can be handed to a wallet as a txmanifest.

Library

Loaded automatically when this page opens: vendor/lwk_wasm.js, the wasm it initialises, and a check that this build really has the Simplicity feature compiled in. It also restores whatever this browser already knew, including your key, your terms and your payout address, so a reload puts you back where you were.

Who signs

Two ways to run the same contract. They are not interchangeable for a single allowance: Humid signs with its own BIP-84 key, so BENEFICIARY_KEY, and therefore the covenant address, differs between them. Pick one before compiling.

Humid reads txmanifest.humid.json from this directory (manifest_version 0.1.0, its own dialect) rather than anything this page builds. It doesn't need a wallet here, since it holds its own funds and its own key, but it does need the relative-timelock patch applied, or every withdrawal is refused with unimplemented-construct. Its FullWithdraw is also still broken in unpatched builds ("pays nothing, so there is nothing to build"), so expect the last withdrawal to fail on this path.

On Humid's “Connect this dapp?” screen, tick processConfidentialTransaction. That checklist starts with nothing selected, and there is a second grant check per method: without it every single action raises its own “Perform a contract action?” prompt, no matter how the session is handled. Connecting itself only re-prompts when the session is actually gone, which, given the extension's worker lifecycle and auto-lock, is often.

These tabs are two views of the same demo, not two identities: switching them changes what you are looking at, never what you can do. What you can actually do depends on what is in this browser, which is what “can fund” and “can withdraw” above report. One browser profile can hold both sides; two profiles is how you get two genuinely separate parties.

Your wallet

A single-key LWK wallet from a BIP-39 mnemonic kept in this browser's localStorage, in plaintext. Testnet play money only. Never put a real mnemonic here.

Humid is the selected signer, so this wallet is not used: Humid funds from its own balance and pays withdrawals to its own change address. The faucet button below would fund this page's wallet, which Humid never looks at. Fund Humid instead, through its own receive address in the extension. You can skip this whole section.

The faucet doesn't send any CORS headers, so this page can dispatch the request but cannot read the reply, and checks your balance a minute later instead.

Choose the allowance terms

These three values are compiled into the contract, so they also determine its address. They cannot be changed afterwards: a different value is a different, unrelated allowance at a different address.

Fund it

Pays an explicit (unblinded) output to the covenant address. That is not a stylistic choice: the contract reads its own amount, so a confidential output here can never be spent and the funds are lost permanently. Leave broadcast unchecked the first time to see what would be built.

Hand the terms to the beneficiary

Nothing here is secret, and there is no protocol for it, so send it however you like. The beneficiary's page re-derives the address from the three parameters and refuses to go on if it disagrees with the address below, so garbled or altered terms are caught before anyone funds the wrong covenant.

Your key

The contract's BENEFICIARY_KEY is a BIP340 x-only public key, and the only way to withdraw is a signature by its private half. Strictly this needs a signer, not a wallet, but in practice a signer almost always comes in the form of a wallet, and treating the two as interchangeable is reasonable outside a demo. This page takes the shortcut: a bare Schnorr keypair, no derivation, no descriptor.

This key is not covered by your wallet's mnemonic. It is 32 random bytes in this browser's localStorage and nothing else. Writing down the twelve words does not back it up: clear this site's data and any allowance made out to this key becomes permanently unclaimable, even though the wallet itself would survive. Copy the secret below somewhere safe if an allowance is funded to it, or treat the whole thing as disposable testnet play.

Load the allowance

Paste what the benefactor sent you. You need no funds and no file they created: the address is derived from the terms, and the current UTXO is found by looking at the chain. What you do need is a signer for the key above; this page uses a bare keypair, but in any real deployment that signer would be a wallet, since that is where keys live.

Or type the terms in by hand

Same three values, if the blob is inconvenient to move. Fill these in and press Load; the fields are shared with the benefactor tab.

Withdraw

Every UTXO at the covenant address is an independent allowance with its own timelock. They are never summed and can never be merged. Each is labelled with the action its current balance makes valid: PartialWithdraw while there is more than one period left, FullWithdraw for the last one, which closes it.

Worth doing once per allowance: it exercises the whole path (compile, sighash, signature, and the contract's own execution) without spending anything. A failure here is the contract or the manifest refusing, not the network.

How this works

What the contract actually enforces

Three values are fixed at compile time and baked into the address: BENEFICIARY_KEY, ALLOWANCE_AMOUNT and MIN_DISTANCE. Every spend needs a BIP340 signature by the beneficiary's key, a BIP68 relative timelock of at least MIN_DISTANCE blocks since the UTXO was created, transaction version 2 or later, and exactly one input.

Which of the two spend shapes is legal is decided by the covenant's own balance, not by the spender. Above ALLOWANCE_AMOUNT, at most that much may leave: the remainder must go back to the very same covenant on output 0, whose script hash the contract compares against its own, with the fee at output 2 and exactly three outputs. At or below ALLOWANCE_AMOUNT the contract doesn't check anything about the outputs at all: the beneficiary may simply take everything, and the covenant ends.

Why the fee comes out of the allowance

Only one input is permitted, so nothing outside the covenant can help pay the fee. It comes out of the amount being withdrawn, which also means an allowance funded with less than a fee can never be emptied.

Why funding must be unblinded

Liquid blinds asset and amount by default, and that is the better default in general. But this contract reads its own balance and output 0's amount, which is only possible against explicit values, and fails outright otherwise. So the covenant's own outputs must be explicit. Output 1, the payout, is never inspected by the contract and could be blinded; this page keeps it explicit only to avoid a blinding pass. The asymmetry worth remembering: getting this wrong on a covenant output strands the funds silently and forever, while getting it wrong elsewhere merely raises an error.

Why this page has to index the chain itself

Neither LWK nor any Simplicity wallet offers "list the UTXOs at this address and tell me which are spendable." That lookup is the application's job, so this page does it directly against Esplora: list the UTXOs, read the chain tip, and compare each UTXO's balance against ALLOWANCE_AMOUNT and its confirmation depth against MIN_DISTANCE. Any real application of a covenant like this needs the same thing.

Why refreshing is slow on purpose

The Esplora instance here is a shared public service nobody in this project operates, and it rate-limits hard, refusing everything for minutes after a burst. So automatic refreshing is paced against how long there is actually left to wait, pauses when the tab is hidden, backs off when a response is slow or refused, and stops altogether after an hour. Press Refresh whenever you want an answer sooner.

Wallet syncs don't touch that instance. They go to a Waterfalls server, which returns the wallet's whole history in a single request. The cost is that the Waterfalls operator learns which addresses belong to the wallet.

Keys and custody

Both the wallet mnemonic and the beneficiary's secret key sit in this browser's localStorage in plaintext, and a separate browser profile is how you get a genuinely separate party. That is fine for testnet play money and completely unacceptable for anything else.
